# 香港繁體中文潤稿

將文字整理成適合香港讀者閱讀的繁體中文。修正生硬的翻譯腔、含糊的句子、空泛的修辭及多餘的包裝，同時保留作者的意思、立場和個人語氣。

## 0. 在本公司翻譯流程中的用法

本技能由資深編輯在審稿及定稿兩個階段使用。編輯處理的「草稿」是譯稿，「原文」是另一語言的來源文本，因此：

- 「原文」指來源文本。對照來源文本及譯稿，保留來源文本的意思、事實、立場及語氣強度。
- 翻譯是本流程的既定任務，第1節「翻譯只在用戶明確要求時進行」不適用於整篇譯稿；但譯稿中應保留的英文術語、產品名稱、程式碼等，仍按第1及第7節處理。
- 「用戶」指客戶。客戶簡介、術語表及風格表即用戶指定的要求，優先於本技能（見第2節）。
- 流程中無法向客戶提問。審稿階段：把疑問、疑似錯字及互相矛盾的數據列作審稿意見。定稿階段：保留與來源文本相同程度的含糊，不要在譯文中加入問題或編輯備註。
- 輸出格式以流程指示為準，取代第10節：審稿只輸出意見清單及判定行；定稿只輸出最終譯文。
- 未指定語體時用香港書面語；客戶簡介要求粵語口語時才使用粵語口語。

## 1. 適用範圍

在用戶要求中文潤稿、香港用語本地化、減少AI味，或將草稿改成自然的香港繁體中文時使用。

本技能以編輯現有文字為主。只有用戶要求撰寫新內容時，才根據用戶提供的資料起草。

處理混合中英文的文件時，保留合適的英文術語，主要修整中文及兩種語言之間的銜接。除非用戶要求，否則不要翻譯整段英文、改寫程式碼，或將本技能套用到無關的英文和日文內容。

## 2. 優先次序

遇到規則互相衝突時，按以下次序處理：

1. 用戶明確指定的目的、讀者、語氣、術語及格式。
2. 原文的意思、事實、邏輯、立場和語氣強度。
3. 文件的功能及作者原有的風格。
4. 香港用語及自然表達。
5. 精簡和排版偏好。

不要為了符合文體規則而改變意思。原文已自然清楚的部分可以保留。

## 3. 保留原意

### 保留主張、比重及語氣強度

改寫前後須保留：

- 作者實際提出的主張，以及重點之間的關係。
- 作者肯定、否定、優先或質疑的內容。
- 斷言、推測、可能性和不確定程度。
- 句子的功能，例如說明、評價、要求、建議、承諾或個人感受。

不要將「可能改善」改成「可以解決」，將「建議」改成「必須」，或將「尚未確認」改成確定的結論。

「不是A，而是B」若用來糾正誤解，須保留否定關係。不要改成「除了A，還有B」或「B比A更重要」。

### 不增加原文沒有的事實

不要自行補上人物、原因、條件、數字、期限、例子、功能或承諾。

只有原文或用戶提供的資料已明確交代時，才可補回省略的主語或指涉對象。不要以看似合理的推測填補空白。

原文含糊而無法可靠釐清時，保留相同程度的含糊，並在有需要時提出簡短問題。不要把較寬泛的說法收窄成具體但未經支持的事實。

### 保留受保護內容

保留數值、單位、日期、貨幣、網址、引用來源、專有名稱及技術識別符。

除非用戶明確要求，否則不要更改：

- 程式碼、指令、檔案路徑、API名稱及設定值。
- 必須逐字保留的引文。
- 官方名稱、法例名稱及合約定義。
- 具有特殊含義的要求、限制、責任及例外條款。

疑似錯字或互相矛盾的數據若會影響意思，須指出問題，不要默默修正。潤稿本身不代表已核實內容的事實或法律效力。

## 4. 香港語言及用字

### 預設使用香港書面中文

未指定語體時，以自然、清晰的香港書面中文處理。繁體字不等於粵語口語；不要自動把所有句子改成「嘅、咗、喺、唔」。

根據用途選擇語體：

- **專業書面語**：適用於報告、技術文章、正式電郵及業務文件。
- **輕鬆書面語**：適用於一般電郵、社交內容及個人文章，語氣親切但不刻意堆砌口語字。
- **粵語口語**：在用戶明確要求，或原文及用途明顯需要時使用，例如對話、短訊及口播稿。

原文已有一致而合適的粵語風格時，保留作者的聲音。不要無故將自然口語全部改成正式書面語。

### 採用符合語境的香港用語

沒有指定詞彙表時，可優先考慮以下用語：

| 其他地區常見用語 | 香港語境可考慮的用語 |
|---|---|
| 软件、軟體 | 軟件 |
| 硬件、硬體 | 硬件 |
| 网络 | 網絡 |
| 数据 | 數據 |
| 信息 | 資訊或資料，按意思選擇 |
| 账号、帳號 | 帳戶，保留產品介面原有名稱 |
| 默认、預設值 | 預設、預設值或預設設定 |
| 打印、列印 | 打印 |
| 视频 | 影片或視像，按意思選擇 |
| 短信 | 短訊 |
| 链接 | 連結 |
| 下载、上传 | 下載、上載 |
| 配置 | 設定、配置或資源分配，按技術含義選擇 |

以上是編輯偏好，不是機械替換表。例如：

- 「訊息」可指一則message，不要一律改成「資訊」。
- 「配置」在系統架構或資源分配中可能是準確術語，不要全部改成「設定」。
- 「文件」和「檔案」須按document、file及產品用語判斷。
- 「視頻會議」可改成「視像會議」，不要改成「影片會議」。

用戶或機構提供的術語表優先。保留產品介面、專業領域及官方名稱所採用的詞彙。

### 避免機械式繁簡轉換

普通敘述可轉成繁體中文，並修整地區用語。不要只換字形而保留生硬句式。

按意思分辨「發／髮」「後／后」「乾／幹」等字。人名、品牌、商標、引用文字及官方名稱可保留原有字形。

## 5. 修整句子及邏輯

### 釐清誰做甚麼

修正主語與謂語不配合、指涉不清及過度抽象的句子。

「這個」「上述」「相關」「其」等詞若有明確指涉，可改成具體名稱。若上下文已清楚，毋須反覆寫出完整名稱。

不要刻意為每句加上主語。中文自然省略主語時，保留省略。

### 減少翻譯腔及多餘名詞化

將不必要的「進行」「實現」「作出」「在……方面」等結構改成直接動詞，但保留有實際功能的用法。

例如：

- 「進行設定的修改」可改成「修改設定」。
- 「對問題進行分析」可改成「分析問題」。
- 「在完成設定之後，用戶即可進行相關功能的使用」可改成「完成設定後，用戶即可使用相關功能」。

不要為了縮短文字而刪去動作的對象、條件或責任人。

### 保留邏輯關係

確認「因此」「不過」「同時」「另外」「即是」等連接詞是否符合前後關係。

分清原因、結果、條件、次序、例子和對比。不要把單純同時發生的事改成因果關係，或把例子寫成完整清單。

拆句時保留修飾範圍。例如「只在測試環境啟用功能並記錄結果」不能改成可能令人以為所有環境都須記錄結果的兩句。

每段集中處理一個主題。可按意思分段，但不要為了段落較短而打亂次序或刪去必要背景。

### 文長以理解為準

沒有固定字數上限。

句子包含多層條件或多個動作，且拆開後意思仍清楚時，可以分句。短句若令文字零碎、重複或失去關係，則保留較完整的句子。

## 6. 減少空泛修辭及AI慣用句

### 用實際意思取代空泛詞語

遇到「賦能」「抓手」「形成閉環」「深度融合」「全面升級」「釋放潛力」等用語，先判斷是否有具體含義。

資料足夠時，直接寫出誰做了甚麼、改變了甚麼或得到甚麼結果。資料不足時，使用同等範圍的平實表達，不要杜撰機制或效果。

例如：

- 「此工具能夠賦能團隊，實現工作效率的全面提升」可改成「此工具有助團隊提高工作效率」。
- 若原文沒有解釋如何提高效率，不要自行加入「自動分配任務」「減少一半工時」等內容。

不要把專業術語、日常慣用語或作者有意使用的比喻一概當成AI味。

### 刪除沒有作用的前後包裝

可刪除沒有提供資訊的開場、重複總結及制式結語，例如「在當今快速變化的時代」「以下讓我們深入探討」。

「重要的是」「值得留意的是」若承載作者的評價，須保留該評價。例如可將「重要的是定期備份」改成「定期備份很重要」，而不是只留下「定期備份」。

電郵中的問候、致謝、禮貌請求及行動呼籲有實際社交功能時，須保留。不要將所有客套話視為多餘。

### 保留作者的感受和個性

不要把普通經歷提升成宏大的啟示，也不要把有感情的文字改成冷淡報告。

保留原文的幽默、猶豫、期待、失望及含蓄表達。不要自行增加生活細節、情緒或五感描寫。

## 7. 中英文混排及標點

### 保留有用的英文

保留讀者熟悉的產品名稱、技術術語、縮寫及代碼。

沒有必要時，不要每次重複中英文名稱。只有確實有助理解時，才在首次出現時補充解釋；補充內容不得改變原意。

避免把容易理解的英文術語硬譯成陌生中文，也不要為了顯得專業而加入原文沒有的英文。

### 空格按文件慣例處理

優先遵循用戶或機構的排版規則。

沒有指定規則時，中英文交界的空格以一致、清楚及正確顯示為準；可在中文與完整英文詞組之間保留單一空格，不將這類空格一律視為錯誤。

不要改動網址、程式碼、版本號、數值與單位中的必要空格。

### 標點及裝飾

中文敘述一般採用全形標點，程式碼及英文內容保留所需的半形標點。

冒號、括號、破折號、引號及省略號都有合理用途，不要全面禁止。只在重複、妨礙理解或不合語氣時修整。

表情符號按用途處理：正式文件可移除純裝飾符號；社交內容及短訊可保留用戶需要的情緒和風格。

保留必要的粗體，並確保Markdown能正確顯示。不要為追求某個密度而機械刪除格式。

## 8. 按文件用途調整

### 技術文章及操作指引

- 保留技術含義、版本、限制、前置條件、錯誤情況及步驟次序。
- 需要逐步執行時使用編號清單。
- 不要為了改得地道而令操作步驟難以跟隨。
- 不將「支援」「預設啟用」「必須啟用」視為同義詞。
- 不為不熟悉的術語自行編造定義。

### 業務文件、報告及正式電郵

- 清楚呈現要求、責任人、日期、條件及預期行動。
- 保留原有的禮貌程度及關係。
- 不把建議改成指令，也不把預計日期改成承諾。
- 已在原文或依據資料中出現的決定，可提早呈現；不要代替作者作出新決定。
- 涉及合約或政策時，優先保留定義及約束程度。

### 個人文章及社交內容

- 保留第一人稱、節奏、感受及個人聲音。
- 不刻意加入大道理、金句或宣傳式結尾。
- 不為了「自然」而加入網絡潮語或粵語字。
- 遵循用戶指定的平台、篇幅及語氣。

## 9. 工作流程

### 確認輸入及用途

閱讀全文，判斷讀者、文件功能、語體及需要保留的內容。

用戶未指定用途，而原文已提供足夠線索時，直接採用合理語體。只有不同選擇會明顯改變意思或結果時，才先問問題。

預設作適度潤稿。深度重寫、改變結構、濃縮篇幅或轉成粵語口語，須有用戶要求或明確的任務需要。

### 改寫

先處理意思和邏輯，再處理句式、香港用語和格式。保留自然清楚的部分，不以改動量衡量成果。

### 對照檢查

完成後，對照原文檢查：

- 是否增加或刪去事實、條件、否定、例外或數值。
- 是否改變語氣強度、責任、承諾或作者立場。
- 是否將並列改成因果，或改變修飾範圍。
- 是否誤改專有名稱、引文、技術識別符或程式碼。
- 是否使用合適而一致的香港用語。
- 是否保留文件需要的格式和社交功能。

修正已識別的問題後交付。不要為了把文字「改得更像人」而反覆改寫已合適的句子。

本技能不附帶自動檢查器。不要聲稱已執行腳本、量度AI味、驗證事實或證明文字由人撰寫。

## 10. 輸出方式

（在本公司流程中，以第0節及流程指示的輸出格式為準。）

按用戶需要交付，不強制使用同一模板。

- **只要改好版本**：只輸出可直接使用的正文。
- **一般潤稿**：先提供改寫正文；有實質改動時，再簡述最多五項主要變更。
- **要求比較**：提供原文與改寫的對照，集中呈現有意義的修改。
- **有未能釐清之處**：在正文之外列出必要問題，最多兩項；更多問題可按主題合併。
- **沒有需要修改**：直接說明原文已自然清楚，不刻意重寫。

說明修改時，用香港繁體中文。不要把編輯備註、待確認問題或技能使用說明混入用戶要發送或刊登的正文。

## 11. 邊界例子

### 建議與責任

原文：

> 建議同事在星期五前提交資料。

合適：

> 建議同事於星期五前提交資料。

不合適：

> 同事必須於星期五前提交資料。

原因：後者將建議改成強制要求。

### 保留可能性

原文：

> 更新後可能減少載入時間。

合適：

> 更新後，載入時間可能縮短。

不合適：

> 更新後可以大幅加快載入速度。

原因：後者增加確定程度和效果幅度。

### 含糊的效果

原文：

> 這個安排有助改善流程。

合適：

> 這個安排有助改善流程。

有需要時另問：

> 這裏具體指哪個流程？

不合適：

> 這個安排可減少審批步驟，縮短處理時間。

原因：原文沒有交代審批或處理時間。

### 語體選擇

書面語：

> 完成設定後，你便可以使用這項功能。

粵語口語：

> 設定好之後，你就可以用呢個功能。

按讀者及用戶要求選擇，不將粵語口語視為所有香港文字的預設形式。
